The Tech Stack Film Crew

A modern web application is like a film crew, where different specialists collaborate to produce a single seamless experience. Let's meet the characters in the UGSkill project:

The Director (Frontend)

React 19 & Vite: Decides exactly what the student sees, draws the video player, captures button clicks, and orchestrates client interactions.

💼

The Producer (Backend)

Express.js & Node: Coordinates everything behind the scenes, checks permissions, handles API routing, and runs the business checks.

⚡

The Runner (Cache)

Redis: A fast runner that keeps temporary statuses (like active exam heartbeats or session tokens) ready in seconds.

The Dual Database Archivists

Instead of relying on a single filing system, UGSkill uses a dual database setup to balance speed, structure, and reliability:

The SQL Ledger (PostgreSQL & Supabase)

Stores transactional, structured data in tables with rigid relationships. This is where student records, course catalog data, placement drives, and verified exam scores live.

Why? Because grades and placements require absolute relational integrity (no orphan records).

The NoSQL Folder (MongoDB)

Stores flexible, unstructured JSON-like documents. This is where polymorphic quiz questions, mock interview responses, and raw webcam proctoring activity events are filed.

Why? Because quizzes can have diverse formats, and proctoring activity streams require high-write speed without rigid schema checks.

LMS Videos & Background Syncing

How user activity is logged in MongoDB and synced asynchronously to PostgreSQL

The Sorting Post Office Metaphor

When a student watches a video lecture, they click "Complete Lesson." Instead of holding up the screen while writing to multiple databases, the system acts like a sorting post office:

📥

The Mailbox (Ingestion)

The student's browser sends a fast completion message. Express logs this event rapidly inside MongoDB without waiting.

📯

The Conveyor Belt (Queue)

BullMQ: Places the sync job onto a Redis-backed queue. The student's video page continues playing immediately.

📮

The Sorting Clerk (Sync Worker)

The background worker picks up the job and writes a clean summary row inside the PostgreSQL database using the Drizzle ORM.

Behind the Scenes: The Sync Worker

Here is the exact background worker code in `ugskill-api` that handles syncing user progress events from MongoDB to PostgreSQL:

CODE 
async function handleActivityToProgress(payload) {
  const { studentId, courseId, lectureId, totalLectures } = payload;
  if (!studentId || !courseId || !lectureId) {
    logger.warn('CDC: missing fields', payload);
    return;
  }
  // 1. Mark lecture complete (idempotent)
  const { alreadyCompleted } = await progressRepository.markLectureComplete(
    studentId, courseId, lectureId
  );
  if (alreadyCompleted) { return; }
  // 2. Upsert progress_summary
  const lectureCount = totalLectures ?? 0;
  await progressRepository.upsertProgressSummary(
    studentId, courseId, lectureCount, lectureId
  );
}

If any critical identifiers are missing from the data...

End the check.

Save progress in the DB. The comment notes this is "idempotent" (no duplicate inserts)...

💡
Aha! What is an "idempotent" operation?

An operation is idempotent if running it 100 times has the exact same effect as running it once. For example, setting a switch to "ON" is idempotent. Toggling the switch is not. Idempotency is crucial for background sync queues because network glitches might cause the same job to be processed twice!

High-Stakes Exams & Proctoring

Real-time anti-cheat signals using WebSockets and event streaming

The Silent Exam Hall Metaphor

During a high-stakes exam, a student's webcam and tab actions are monitored live. Rather than refreshing a database every second (which would crash the server), the app operates like a silent exam hall:

🔌

The Dedicated Line (WebSockets)

A continuous open pipe connects the browser directly to the server. Information flows instantly in both directions with zero request delays.

🎟️

Exam Channels (Namespaces)

A special `/tracking` namespace separates tracking alerts from generic chat or exam question updates, keeping traffic clean.

💓

Keep-Alive check (Heartbeat)

The browser sends a heartbeat every 30 seconds. If it stops, the system knows the student disconnected or closed the window.

Behind the Scenes: Streaming the Flags

Let's trace how the server handles anti-cheat event alerts via the WebSocket socket listener:

CODE 
socket.on('flag:event', async ({ attemptId, eventType, severity, metadata }) => {
  if (!attemptId || !eventType || !severity) {
    socket.emit('error', { message: 'Missing fields' });
    return;
  }
  const room = `tracking:${attemptId}`;
  const alert = { attemptId, eventType, severity, userId, timestamp: new Date().toISOString() };
  try {
    const attempt = await examAttemptRepository.findAttemptById(attemptId);
    await proctoringService.ingestEvent({
      attemptId, examId: attempt.examId, studentId: attempt.studentId,
      type: normalizeEventType(eventType), severity: severity.toUpperCase()
    });
  } catch (err) { logger.error('Failed to persist flag', err); }
  // Broadcast alerts
  trackingNS.to(room).emit('flag:alert', alert);
  trackingNS.to('admin:monitoring').emit('flag:alert', alert);
});

Placements Hub & Live GDs

Verifying applicant qualifications and managing collaborative interview structures

The Gatekeeper Metaphor

Before a student is allowed to enter a restricted room on campus (the Placement Interview rooms), a Gatekeeper checks their pass:

📈

The Pass Check (CGPA Cutoff)

Every company sets a custom academic threshold. The gatekeeper verifies the student meets this requirement before booking slots.

📄

Portfolio Check (Resume Validation)

No resume, no entry. The system ensures a valid resume URL is linked to the student profile to prevent empty profiles from reaching HR.

🔑

Official Stamp (Postgres Registration)

A transactional record is created in PostgreSQL with status set to 'registered', serving as the official ticket to proceed. Deleting a drive triggers a Cascade Delete, wiping out registrations in PostgreSQL to avoid orphan records.

💡
Steering your AI Assistant

When requesting changes to placement eligibility rules (e.g. adding branch/major cutoffs), direct the AI specifically: "Modify the eligibility checks in the placement service to compare student branch with allowed branches from the drive configuration."

Behind the Scenes: The Gatekeeper Code

Let's trace the backend code checks in placement.service.ts that run when a student clicks register:

CODE 
export const registerForDrive = async (studentId, data) => {
  const drive = await placementRepo.getDriveById(data.driveId);
  if (!drive) {
    throw new NotFoundError('Drive not found');
  }
  const existing = await placementRepo.getRegistration(studentId, data.driveId);
  if (existing) {
    throw new AppError('Student already registered', 409);
  }
  const user = await userRepo.findById(studentId);
  if (!user) {
    throw new NotFoundError('User not found');
  }
  if (drive.eligibility && drive.eligibility.cgpaCutoff !== undefined) {
    const cutoff = drive.eligibility.cgpaCutoff;
    const userCgpa = user.cgpa ? Number(user.cgpa) : 0;
    if (userCgpa < cutoff) {
      throw new AppError('CGPA below required cutoff', 422);
    }
  }
  if (!user.resumeUrl) {
    throw new AppError('Resume is required', 422);
  }
  const registration = await placementRepo.insertRegistrationPg({
    studentId,
    driveId: data.driveId,
    status: 'registered'
  });
  return registration;
};
